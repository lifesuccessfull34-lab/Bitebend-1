Phase 8 — Takeaway Sessions Using The Same Billing Architecture

Goal:

Use the same Session → Bill → Screenshot → Verification workflow for Takeaway orders.

Current problem:

Takeaway orders are still treated as individual orders.

Result:

* Multiple takeaway orders from the same customer appear separately.
* Separate payment bills may be generated.
* Dashboard becomes order-centric instead of session-centric.

New requirement:

Takeaway orders must also use sessions.

Session grouping rules:

Dine-in:

* Group by tableNumber (existing behavior)

Takeaway:

* Group by customer phone number

Database changes:

Extend table_sessions:

Add:

* session_type ('dine_in' | 'takeaway')
* customer_phone (nullable)

Requirements:

1. Order creation logic

Current:

if table exists:
attach to table session
else:
sessionId = null

New:

if table exists:
find/reuse active dine-in session by tableNumber

else:
find active takeaway session by customer_phone

```
if found:
    reuse session

else:
    create new takeaway session
```

Then:

orders.session_id = session.id

2. Session lifecycle

Dine-in:

* No change

Takeaway:

* Session remains active while customer keeps ordering
* Multiple orders from same phone must join the same active session

Important:

DO NOT implement time-based expiry.

Takeaway session closes ONLY when:

Bill approved successfully

Meaning:

Approve Payment must continue doing:

session_bill.status = paid
table_session.status = closed
all orders.paymentStatus = paid

This close behavior must now apply to takeaway sessions as well.

3. Dashboard

Session Cards must display both:

Dine-in session:
Table T3

Takeaway session:
Takeaway
+919876543210

Show:

* Session Type
* Order Count
* Item Count
* Total Amount
* Status

Expanded view must continue showing all orders.

Existing actions must continue working:

* Generate Bill
* Send Bill
* View Screenshot
* Approve Payment
* Reject Payment

4. Billing

No billing changes.

Keep:

Session
→ Bill
→ Screenshot

ownership exactly as today.

5. Screenshot Matching

No changes.

Continue matching:

incoming WhatsApp phone
→ session_bill.customer_phone
→ bill.status = 'sent'

6. History

History page must show:

* Session Type
* Table Number (if dine-in)
* Customer Phone (if takeaway)

7. Legacy Compatibility

Existing orders:
session_id = null

must continue working.

Do not migrate old data.

Before coding show:

* Database changes
* API changes
* Dashboard changes
* Any risk to existing dine-in sessions

After implementation show:

* Files changed
* Migration applied
* Example dine-in session
* Example takeaway session
* Verification that two takeaway orders from the same phone join the same session
* Verification that approving the bill closes the takeaway session

Important:

This is not a new billing system.

This is only extending the existing Session Architecture so both Dine-In and Takeaway use the same Session → Bill workflow.
