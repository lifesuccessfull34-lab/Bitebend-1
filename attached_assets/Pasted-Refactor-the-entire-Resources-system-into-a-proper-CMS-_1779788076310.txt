Refactor the entire Resources system into a proper CMS + public portal architecture.

GOAL:
Super Admin controls all content. Public only consumes it.

---

1. SOURCE OF TRUTH (NO CHANGE)

Keep ONE database table:

resources

All content MUST be stored here.

Remove:

* localStorage resource logic
* mock resource arrays
* frontend-only resource editing systems
* any per-browser resource overrides

---

2. SUPER ADMIN CMS (EDITING LAYER)

Route:
/portal/admin/resources  (or /super-admin/resources if already exists)

This is the ONLY editable interface.

Super Admin can:

* Create resources
* Edit resources
* Delete (soft delete only)
* Approve / reject (if workflow exists)
* Set publishAt / expireAt
* Set visibility (public / restaurant / admin)
* Feature resources
* Upload videos / PDFs / links / FAQs

This page = CMS (content management system)

No other role can create or directly publish resources.

---

3. PUBLIC RESOURCE PAGE (READ ONLY)

Route:
/portal/resources

This page is:

* 100% read-only
* accessible without login (public)
* consumes ONLY backend API

It should display:

* Bitebend introduction
* Tutorials (registration, onboarding)
* Demo videos
* Pricing / plans
* FAQs
* Support guides

BUT ONLY content returned by backend.

No mock data allowed.

---

4. BACKEND ENFORCEMENT (CRITICAL)

Update API:

GET /api/resources

Must enforce server-side filters ONLY:

* status = 'active'
* approvalStatus = 'approved'
* publishAt <= now
* expireAt is null OR future
* deletedAt IS NULL
* visibility rules

NEVER rely on frontend filtering.

---

5. ROLE RULES

Super Admin:

* full CRUD
* approve/reject/publish

Restaurant Owner:

* NO resource creation
* NO resource editing
* can ONLY view public/restaurant-visible resources

Guest:

* only public resources

---

6. VISIBILITY MODEL

Add field:

visibleTo: 'public' | 'restaurant' | 'admin' | 'all'

Examples:

* onboarding tutorials → public
* payment setup → restaurant
* internal docs → admin

---

7. ROUTE CLEANUP

Remove or redirect:

/restaurant/resources → /portal/resources

There should be ONLY ONE public resources page.

---

8. SYSTEM DESIGN RULE

Architecture must follow:

Super Admin CMS → Database → Public API → /portal/resources

NOT:
Frontend mock data or local storage.

---

9. FINAL GOAL

/portal/resources becomes:

* Bitebend public knowledge hub
* onboarding funnel
* marketing + education page

Super admin panel becomes:

* full CMS control center
